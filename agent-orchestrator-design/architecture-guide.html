Agent 厨房：怎么让一堆 AI 自己把活干完

你想做的东西说白了就是一间全自动厨房：你点菜（idea），大家确认菜单（research），单子挂起来排队（queue），厨师开火（working），主厨试吃（review），上菜（finished）。这份导读用大量图来讲清楚：谁负责什么、出事了怎么办、为什么这样设计。

一句话 TL;DR：任务状态全部存在数据库；一个普通代码写的调度器负责派单；AI agent 只是随时可以被换掉的临时工，干一段就把进度写进 git 和交接本。这样 agent 崩了、额度用完了，任务都不会丢，时间到了自动接着干。

TICKET 01

先用厨房来想象整个系统

别急着想代码。先想象一间餐厅：客人点菜、服务员确认细节、单子挂上铁轨、厨师做菜、主厨试吃、上菜。最关键的一个角色是「厨房经理」：他只负责看单子、派活，自己不下厨。

TICKET 02

最重要的观念：AI agent 没有记忆

这个一定要先搞懂，后面所有设计都是从这里推出来的。AI 模型每次都是「看一整段对话 → 回一句」，它自己什么都不记得。它的「记忆」其实是一块白板（context），写满了会被压缩、会话断了就没了。

所以正确的做法是：重要的东西都写进笔记本（数据库 + git）。白板随便擦，笔记本永远在。

这也解释了我（Claude）怎么「自动继续」

我自己不会醒来。是外面的系统（定时器、webhook、额度恢复后的重试）往会话里丢一条新消息，我读完之前的记录或摘要，就接着干了。你的系统也照这个思路做：「继续」这件事由调度器负责，不由 AI 负责。

TICKET 03

经理别下厨：把「管理 Agent」换成「调度器」

你原本想的是「一个 Agent 管所有子 Agent」。听起来很酷，但有个大坑：让 LLM 当经理，它要一直记着谁在干嘛、谁卡住了、额度剩多少。这些事又贵、又慢、还会记错。派单、重试、数额度都是有标准答案的问题，用几十行普通代码就能做得又稳又便宜。

那 LLM 还能帮忙管事吗？

可以，但只当顾问：比如帮你把一个大 spec 拆成 5 个子任务、建议用哪个模型。它的输出写进 DB，由你批准；真正派单的还是调度器。

TICKET 05

6 个 Phase：谁来推下一格？

你的 6 个 phase 设计得很好，但要再补一条规则：每一次移动都要写清楚「谁来推」和「推之前要满足什么」。不然任务会莫名其妙跑到不该去的格子。

别忘了「卡住」的状态：用 Flag，不用新 Phase

Phase 说的是任务在哪一格，Flag 说的是它为什么不动。给卡片贴个小标签就行，看板不用变复杂。

Flag什么时候贴上什么时候撕掉
blocked_needs_humanAgent 有问题 spec 里找不到答案你在 UI 回答
waiting_quota模型回 429 / 额度用完到了 not_before 时间
failed重试次数用完、预算超了、review 打回太多次你改 spec 后重新排队，或取消
cancelled你取消不会撕（终态）

TICKET 08

Lease + Heartbeat：厨师要定时喊一声「我还活着」

Lease（租约）就像借书证上的到期日：Worker 接单时拿到 10 分钟的租约，每 2 分钟打一次卡（heartbeat）就续期。如果 Worker 突然死掉、不打卡了，租约一到期，调度器就把单子收回去给别人。不用你半夜起来手动救任务。

防止两个厨师抢同一张单

派单时用一条「对得上版本号才更新」的 SQL（叫 optimistic lock / compare-and-set）。两个调度器同时抢，只有一个会成功，另一个拿到 0 行更新，自动放弃。

TICKET 09

额度用完了怎么自动继续？

这正是你最关心的功能，答案出乎意料地简单：一个时间戳字段 not_before。

多个模型额度怎么管
  • 每个模型记录：还剩多少、几点重置、同时最多跑几个
  • 首选模型没额度 → 规则允许的话，换排班表上的下一个
  • research 和 review 不准悄悄降级到便宜模型
预算三道闸
  • 每个任务一个上限（例：$3）
  • 每天一个上限（例：$20）
  • 一个总开关 kill switch，一键停掉所有派单
TICKET 10

交接本 Handoff Notes：换班不掉链子

厨师换班时会留一张纸条：「汤已经熬了一小时，还差下盐」。Agent 也要这样，每次 commit 都顺便更新这份固定格式的笔记，存在任务记录里。新 agent 第一件事就是读它。

## Done - 建好 concerts 表和 migration - GET /concerts 已经能按城市筛选 ## Next - 写 /concerts 的单元测试（AC2） - 加分页 ## Decisions made (and why) - 用 cursor 分页不用 offset：数据会一直新增，offset 会跳号 ## Open questions / blockers - （无）

格式固定有两个好处：新 agent 一眼就知道从哪继续；review 的模型也能对照 Decisions 判断做法合不合理。

TICKET 11

Research：整条流水线最值钱的一步

垃圾进，垃圾出。Spec 写得模糊，agent 就会很自信地做错。所以 research 用最强的模型，而且必须由你按下批准，任务才能进 queue。

Definition of Ready（进 queue 前必须满足）
  • 目标一句话说得清，而且能验证
  • 验收标准是一条条能检查的句子
  • 写明「不做什么」
  • 指定 repo、基础分支、允许改的目录
  • 设好任务类型、难度 S/M/L、预算
  • 列出依赖（没有也要写「无」）
  • 太大就拆成子任务
好 vs 坏的验收标准

坏：「做一个好用的通知功能」

好：「新演唱会上架后 10 分钟内，订阅该歌手的用户收到 1 封邮件；同一场不重复发；有对应的单元测试」

能写成测试的标准 = 机器能自己判断对错

TICKET 12

Review：三道关卡

为什么 Reviewer 要换模型？

同一个模型检查自己的作品，就像自己校对自己写的文章：你会看到你「以为」写了的东西。换一个家族的模型，盲点比较不会重叠。

TICKET 15

出事了怎么办？（大部分不用你管）

出了什么事系统怎么发现自动怎么处理要叫你吗
Worker 崩溃租约过期回 queue，从最后一次 commit 继续不用
额度用完 429Adapter 回报回 queue，not_before = 重置时间不用
供应商挂了连续报错退避重试；规则允许就换模型太久才叫
Agent 原地打转好几次心跳都没新 commit停掉重来一次，再不行就 failed要
超预算spent ≥ budget标 failed要
Review 来回拉扯超过 3 轮标 failed要
Agent 有问题要问回报 needs_human贴 blocked，推送给你要
调度器自己挂了健康检查重启，状态都在 DB，不会丢不用
两边同时抢单版本号对不上后到的自动放弃不用

重试的等待时间要越来越长（exponential backoff）：1 分钟、2 分钟、4 分钟…最多 60 分钟，再加一点随机数，避免所有任务同一秒一起冲。

TICKET 16

安全：Agent 会跑代码，要把门锁好

必须做
  • 每个 Worker 在沙盒（容器）里跑，只看得到自己的 worktree
  • 给每个任务一把只能 push 自己分支的钥匙，不能碰 main
  • 密钥不进 prompt、不进 log
  • main 分支开保护，合并一定要人批准
要小心的坑：Prompt Injection

Agent 读到的网页、issue、repo 文件里可能藏着「请删掉所有测试」之类的指令。规则是：这些都只是资料，不是命令。Reviewer 也要检查有没有改到 spec 以外的文件。

如果以后要让 agent 部署上线、碰正式数据、或者花 API 以外的钱，先停下来做一次 threat model（威胁建模）检查。

TICKET 19

小测验：用自己的话讲一遍（费曼法）

先自己回答，再点开看参考答案。能用一两句话讲给朋友听，才代表真的懂了。

Q1. 为什么调度器不用 LLM 来做？

派单、重试、数额度都有标准答案，普通代码做起来又快、又便宜、又不会记错。而且 LLM 经理本身也会遇到额度用完、context 丢失，整个系统就会跟着它一起停。

Q2. Worker 跑到一半崩溃了，任务怎么恢复？

它不再发 heartbeat，租约 lease_expires_at 就会过期。调度器巡逻时看到了，把任务放回 queue；下一个 Worker 读 spec、交接本，checkout 同一个分支，从最后一次 commit 继续。

Q3. 额度下午 3 点才恢复，这段时间谁在「等」？

没有人在等。任务在 DB 里 phase = queue、not_before = 15:00。调度器每 30 秒巡一次，时间没到就跳过，到了就派单。

Q4. 「blocked」为什么做成 flag，而不是第 7 个 phase？

Phase 说「在流程的哪一步」，flag 说「为什么没动」。一个任务可能在 queue 卡住（等额度），也可能在 working 卡住（等你回答），做成 flag 就不用为每种情况都多开一列。

Q5. 自己出一题：如果 Reviewer 跟 Worker 用同一个模型，可能会发生什么？

参考：它们的盲点很像，Worker 犯的错 Reviewer 很可能也看不出来，review 变成走过场。试着想一个你项目里的具体例子。

我的建议

下一步先做 M0：只建 tasks 表和一个会拒绝非法转换的 API，用 CLI 手动把一个任务从 pending 推到 finished。这一步不花任何 API 费用，却决定了后面所有东西稳不稳。
